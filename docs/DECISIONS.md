# Decisions

Technical and process decisions, newest last. Plain language: what, why, what else was considered. Product decisions about the design are in `DESIGN.md`.

### D1 · 2026-10-22 · Agents build, review and merge
The owner doesn't review code. Every change is a PR; it merges when CI is green and the reviewer agent posts `VERDICT: APPROVE`. Verdicts are PR comments because all agents use the owner's GitHub login, and GitHub doesn't let an account approve its own PR. Replaced in part by D42 (the approval must name the head commit).

### D2 · 2026-10-22 · Agents run in T3 Code on the owner's Mac
Uses the existing Claude subscription, so there's no per-token bill. Considered: GitHub Actions with an API key (runs unattended, but costs more and is harder to keep an eye on).

### D3 · 2026-10-22 · Models matched to the job
Sonnet for normal building, Opus for the parser, planning and review, Haiku for mechanical work, Fable only for escalation. Details in `AGENT-PLAN.md`. Since D21 the reviewer is the native Opus agent, and the chore agent runs on Haiku (`.claude/agents/chore.md`). **Amendment (PUB.22, 2026-10-25):** the first wording said the reviewer is "a different model from the main builder, so they don't share blind spots". That was not true for the parser PRs, where `builder-heavy` and the reviewer are both Opus. What the separation really is: a separate agent with its own prompt, no Edit or Write tools, and its prompt forbids editing code (it keeps Bash for `gh` and running checks) and a fresh context that sees only the PR and the brief. Model-family independence is not claimed.

### D4 · 2026-10-22 · No GitHub branch protection
The repo is private on a free plan, and branch protection for private repos needs a paid plan. The orchestrator enforces "CI green before merge" itself instead. Revisit if the repo goes public. Replaced in part by D41 (a ruleset on the public repo, PUB.3).

### D5 · 2026-10-22 · npm, Vitest, GitHub Actions
npm comes with Node, so there's nothing extra to install or explain. Vitest is fast and handles TypeScript out of the box, which suits the parser (pure functions, fixture tests). Visual checks come from the QA agent rather than snapshot tests. GitHub Actions' free private-repo minutes are more than enough.

### D6 · 2026-10-22 · Release policy
Web (satanen.io) deploys automatically from a green `main`, since a bad deploy is undone in a minute. Store releases need the owner's written OK: they are public, slow to undo and run under the owner's developer account.

### D7 · 2026-10-22 · Routine building on DeepSeek
The owner has DeepSeek API access in T3. To save Claude usage, `builder` runs on DeepSeek V4 Pro and `chore` on DeepSeek V4.1 Flash. A smoke test confirmed they can read the repo and use git/gh. Claude keeps orchestration, planning, the parser, review, QA (it needs T3's screenshot tools and image understanding) and escalation. Limits: no secrets on DeepSeek; paid models only. Replaced in part by D8 (builder) and D3/D21 (chore on Haiku). Code (not secrets) is sent to DeepSeek's API, which is acceptable for an app that shows public content. Builder is a trial: if its PRs need too many Claude review rounds, it goes back to Sonnet (rule in `agents/ORCHESTRATOR.md`).

### D8 · 2026-10-22 · Builder back on Sonnet
The DeepSeek builder trial hit its stop rule: all three of its PRs (#3, #6, #9) needed a second review round. The fixes were real: a helper that would have changed Yle's text, text styles that would have rendered wrongly on Android, and cut-off tab labels. Each extra round costs a Claude review and QA run, which outweighs DeepSeek's lower price, so `builder` runs as the native Sonnet agent again. Chores stay on DeepSeek Flash: its two chore PRs merged first time. (Replaced in part by D3 and D21: chore runs on Haiku.)

### D9 · 2026-10-22 · Reviews on DeepSeek, model choice by the orchestrator
The owner keeps hitting the Claude Pro usage limits. The Opus reviewer runs on every non-chore PR, making it the biggest repeated Claude cost after the orchestrator, so reviews of `builder` PRs move to DeepSeek V4 Pro as a trial. It's a different model family from the Sonnet builder, so they still don't share blind spots. Parser (`builder-heavy`) PRs keep the Opus reviewer, because that's where silent mistakes hurt most. Risk: DeepSeek's own builder PRs needed second rounds (D8), so it may also miss problems; stop rule in `agents/ORCHESTRATOR.md`. The orchestrator may also move single tasks between Claude and DeepSeek when that's cheaper overall, never for secrets, the parser or QA. Considered: Sonnet reviewer (same model as the builder, so shared blind spots) and keeping Opus (uses up the Pro limits). Replaced by D21 (DeepSeek reviews stopped).

### D10 · 2026-10-22 · The proxy passes Yle's data through unchanged
The Cloudflare Worker in `proxy/` only adds the key, checks the page number, caches, and turns Yle's errors into plain JSON (`not-found`, `upstream`). The parser stays in the app. Two routes: `/v1/pages/{n}.json` and `/v1/images/{n}/{sub}.png`, on `api.satanen.io`. The browser only lets satanen.io and the local dev server read it (CORS). That doesn't stop scripts, but it does stop other websites from quietly running on our proxy and our Yle quota. `proxy/` is its own small package, so Wrangler (Cloudflare's large tool) isn't installed into the app. Its tests are plain Vitest with a fake `fetch` and cache, the same tool as the rest of the repo. Considered: running the parser in the Worker. Parser fixes would then reach Android users without a store update, but the free plan's 10 ms CPU limit per request is tight for long pages, and the app and Worker would have to change in step. Revisit in M4 if waiting for store updates to ship parser fixes becomes a problem. Also considered: Cloudflare's Workers test pool (`@cloudflare/vitest-pool-workers`). It's more realistic but heavier and tied to specific Vitest versions, and the logic here is simple enough to fake.

### D11 · 2026-10-22 · Edge cache of 45 s, plus a last good copy
**Replaced by D39 B** (25.10.2026): the single 45 s became one limit per kind of page; the 24 h last good copy stays. Every page and image is kept for 45 s in Cloudflare's cache, and the app or browser may keep it 15 s more, so a page is never more than 60 s old. That's inside the 30–60 s in the plan, and each page costs Yle at most about one request a minute per Cloudflare data centre. Missing pages (404) are kept 30 s. Errors are never cached. Yle's API is labelled experimental, so the Worker also keeps the last good copy of each page for 24 h. If Yle is down or slow (over 8 s), readers get that copy marked as old instead of an error. The app can then show "Päivitetty 14:32". This needs a real domain (`api.satanen.io`), because Cloudflare's Worker cache doesn't work on the free `*.workers.dev` address. Considered: Cloudflare KV storage (works on workers.dev, but the free plan allows only 1,000 writes a day, which a 45 s cache uses up in minutes), and Cloudflare's built-in fetch caching (less control over errors and the old copy).

### D12 · 2026-10-22 · The Worker is deployed from the owner's Mac
Agents already run on the owner's Mac (D2), so the orchestrator deploys the Worker with `wrangler deploy` after a merge that touches `proxy/`, then runs a smoke test. The owner allows it once through Cloudflare's own login page (`wrangler login`, one click), so there's no API token to create, copy or keep safe. The Yle keys go into the Worker once, as Cloudflare secrets, read from `.env.fixtures` (was `.env` before PUB.18) by a Claude agent. They are never stored in GitHub. Considered: deploying from GitHub Actions. It works with the Mac switched off, but it needs a Cloudflare API token with the right permissions stored in GitHub, which means more steps for the owner and one more place a secret lives. Revisit if deploys ever need to happen while the Mac is off.

### D13 · 2026-10-22 · Section map refreshed weekly by GitHub Actions, through a pull request
A scheduled GitHub Action runs `npm run section-map -- --live` every Monday. It fetches the index pages through our public proxy, so no Yle key is needed in GitHub, and it opens a PR only when the map changed. The map stays a reviewed file in git. A bad parse or a Yle outage can't silently empty the type-ahead: the script refuses to write a map that shrinks by more than 20 %, and CI checks the PR. The live index pages are saved separately from the parser's test fixtures, so those fixtures never change by themselves. Downside: Android users get a new map only with an app update. That's acceptable, because sections change rarely and typing any page number always works. Considered: a Worker cron job writing the map to KV for the app to download (updates the phone app without a release, but adds KV, a new endpoint and a runtime path with no review), and building the map on the phone from live index pages (about 15 fetches on every start).

### D14 · 2026-10-22 · Pages kept on the phone, loaded through one small hook
Every screen gets its page through one `usePage(n)` hook in `src/data/`. It shows the copy saved on the phone straight away, then fetches a fresh one from the proxy. If the network is down, the reader keeps the saved copy marked "Päivitetty 14:32 · ei yhteyttä". The 30 most recently read pages are kept, as the raw Yle data rather than the finished layout, so parser fixes also improve pages that were saved earlier. Screens that ask for the same page at the same time share one request, and a page fetched in the last 15 s isn't fetched again (the proxy's own cache is 45 s, D11). On the web, "the phone" means the browser's local storage, which has a limit of about 5 MB. 30 pages fit comfortably, and if storage is ever full the oldest page is dropped. Considered: TanStack Query, a popular data-fetching library. It does this and more, but it's a large dependency for one hook, and saving to the device would need extra plugins anyway. Also considered: saving the finished reader layout (faster to show, but stuck with old parser mistakes). Replaced in part by D26 (80 saved pages instead of 30) and D39 (the 15 s rule now follows the proxy's limit per kind of page).

### D15 · 2026-10-22 · Favourites, recent pages and settings in AsyncStorage, no state library
AsyncStorage is the standard Expo way to keep small data on the device (on the web it uses the browser's local storage). It's the only new dependency in M3. Each kind of data has its own key with a version in the name (`satanen:v1:favourites`), so a future format change can convert old data instead of losing it. Reading never crashes the app: missing or damaged data falls back to the default (no favourites, system theme). Screens stay in sync through React's built-in `useSyncExternalStore`, so starring a page shows up on the favourites tab at once. Considered: Zustand or Redux (state libraries; not needed for three small lists) and expo-sqlite (a database; far more than needed).

### D16 · 2026-10-22 · Jump sheet, drawer and settings are ordinary routes, no drawer library
Every screen has its own address: `/105` for a page, `/siirry` for the jump sheet, `/valikko` for the ☰ drawer, `/asetukset` for settings. The back button, the browser's back button and shared links then all just work. The jump sheet opens as a modal (a sheet over the current screen) and the drawer as a see-through modal that slides in from the left with React Native's built-in animation. Considered: React Navigation's drawer. It needs two large native modules (gesture handler and Reanimated) for one menu that opens from a button anyway.

### D17 · 2026-10-22 · The web app is a single-page app on Cloudflare, deployed from the Mac
`npx expo export` builds the web app into a `dist/` folder: one HTML page plus scripts. It's served by a code-free Cloudflare Worker that only hands out those files (Workers "static assets", config in `site/wrangler.toml`) on `satanen.io`. Any unknown address such as `/105` gets the same page, and the app then shows page 105. It's deployed the same way as the proxy (D12): the orchestrator runs `npm run deploy:web` on the owner's Mac after a merge, then a smoke test. It reuses the Wrangler already in `proxy/`, so nothing new is installed. The HTML and service worker are never cached, so a new release reaches readers on their next visit. The script files have unique names per build and can be cached for a year. Rolling back = deploying the previous commit. Considered: Cloudflare Pages (works too, but Cloudflare now steers new sites to Workers, and it would be a second product to learn); building a separate HTML file per page (Expo's "static" output; useless here, because the content is live and fetched in the browser); deploying from GitHub Actions (needs a Cloudflare token stored in GitHub, see D12).

### D18 · 2026-10-22 · Home-screen install: web manifest plus a small hand-written service worker
To be installable, the site needs a manifest (name, icons, colours) and proper icons, rendered once from the logo SVGs. To open with no network, a service worker keeps the app's own files: the page loads from the network when it can and from the saved copy when it can't. The worker never touches teletext data. Offline pages come only from the copies in D14, so there's one place that decides what's old. The worker is about 50 lines and written by us. The list of files it keeps is generated after each build and tested. Considered: Workbox, Google's service-worker toolkit (reliable, but its build tool pulls in a large set of dependencies for something this small), and no service worker (Android could still install the app, but it would show a browser error when offline).

### D19 · 2026-10-22 · Front page built from page 100, sections from page numbers
The front page is page 100's headlines, regrouped. The first headline becomes the lead story, and the rest are grouped by their page number (102–129 Kotimaa, 130–159 Ulkomaat, 160–189 Talous, 2xx Urheilu). That's how Teksti-TV itself numbers sections, so no guessing from the text is needed. The lead card's short intro is the first paragraph of the lead article, fetched separately: one extra request, cached like any page. Text is never shortened or reworded (Yle's licence). Long text is clamped on screen with "…", and the full text is one tap away. The logic is a pure function tested on the saved page 100. Considered: reading section names from the section index pages (102, 130, 160…). That's more requests on every start for the same result.

### D20 · 2026-10-22 · Go online hidden from search engines until Yle answers
The owner chose option A. satanen.io goes online when M3 is done, with `X-Robots-Tag: noindex`, and the link is shared only with friends and testers. The hiding is removed after Yle's reply (or when the owner says so). Not the same as secret: anyone with the link can open it. The dark theme is called "Tumma" in the UI (the owner's wording), replacing "Grafiitti".

### D21 · 2026-10-23 · DeepSeek reviews stopped, back to the native reviewer
The DeepSeek reviewer approved the jump sheet (PR #34) and called the failing Esc key "a preview artifact". QA then showed it was a real bug: the number field swallowed the Esc key press, so the sheet could not be closed with the keyboard. That triggers the stop rule from D9. The orchestrator can still pick DeepSeek for one-off reviews of small pure-logic PRs (the chore agent now runs on Haiku, see D3). Replaced in part by D42 (the merge rule is stricter). ### D22 · 2026-10-23 · Text follows the browser's text size through a factor in the theme
The fonts in the design tokens are fixed pixel numbers, so on the web they ignored the browser's text-size setting (a 32 px root left the headline at 27 px). The theme now reads the page's root font size, divides by 16 and multiplies every text style (size, line height, letter spacing) by that factor, capped at 3. On phones the factor stays 1, because React Native already follows the system font size there. Spacing and the 44 px touch targets are not scaled. Tested as a pure function (`src/theme/scale.ts`). Considered: rem units in the styles (React Native's styles have no rem on phones, so every screen would need two code paths), and a library for responsive text (a new dependency for ten lines of code). Same change: all screens sit in one centred column, 640 px wide at most (`src/ui/AppColumn.tsx`).

### D23 · 2026-10-23 · Tab-bar labels follow the text size only up to 150 %
Four tab labels share a 390 px bar, and "Suosikit" is one word that cannot wrap, so at 200 % text it needs about 105 px against about 97 px per tab. Letting it grow would cut the word ("Suosi…"). The labels (not the headings, body text or bar height) stop growing at 150 %. Each tab also has an icon and a screen-reader name, so nothing is lost for people who rely on large text. The text size is also read live now, so changing it while the app is open updates the layout (D22 read it only at load and on resize). Considered: shorter or reworded labels (the owner chose the names), a scrolling tab bar (unusual for four tabs). Revisit if testers on small phones with large text report trouble. Amended in M3.22: the bar now has five tabs (Etusivu added), so the cap is 125 % instead of 150 % to keep "Suosikit" whole at 390 px.

### D25 · 2026-10-23 · News feeds are built from Yle's section index pages
The three feeds list the headlines on Yle's section index pages: Uutiset uses 102 Kotimaa and 130 Ulkomaat, Talous uses 160 and Urheilu uses 201. Those pages are Yle's own list of current stories, in Yle's order, at one request each, and they already carry the headlines, so the list can be shown before any article loads. Rules, each with a fixture test: only the day's news list is used (the headline rows after the date row, such as "Keskiviikon uutisia:" or "Keskiviikko"). That leaves out 160's service links after the blank row (rates, stock pages) and the promos above 201's date row. Page ranges and links to index pages are never items. Each page appears once (the first headline is kept, as on the front page, D19). The sports feed keeps 2xx and 6xx pages (Yle puts European football on 6xx) and drops others, such as a 3xx TV listing. If the date row can't be found, every headline row is used, so a layout change at Yle shows too much rather than nothing. Uutiset's "Kaikki" chip is Kotimaa, then Ulkomaat, each in Yle's order. On 21.10.2026 that gave 18 items for Uutiset, 6 for Talous and 9 for Urheilu. Considered: walking pages by number with Yle's next-page links (that reaches pages that aren't news and gaps that answer 404, and costs a request just to learn each headline), and sorting by article time (every article would have to load before anything could be shown, and Yle's editorial order would be lost). **Update (2026-10-27):** on a Tuesday, 102 and 130 list the new stories at the top with no label and put the date row (`Maanantain uutisia:`) over yesterday's, so "only the rows after the date row" showed only yesterday's news (owner report). Kotimaa and Ulkomaat now take the headline rows above the date row too, then the ones under it, in Yle's order. Talous and Urheilu keep the old rule: 201 has promos above its date row.

### D26 · 2026-10-23 · First paragraphs load as the reader scrolls, at most 4 at a time
Each item's first paragraph needs a request for its article. The feed asks only for the items on screen plus the next 6, never more than 4 requests at once, and fetches more as the reader scrolls. The requests go through the same page source as every other screen (D14). That means shared requests and the freshness rule (15 s, now the proxy's limit up to 60 s: D39, FR.3), and an article opened from the feed shows at once. Reading the whole Uutiset feed is about 20 proxy requests (Talous about 7, Urheilu about 10). The proxy's 45 s cache (D11) holds Yle to about one request per page per minute per Cloudflare data centre, however many people read. Cloudflare's free plan allows 100,000 Worker requests a day, about 5,000 full feed reads. Revisit when the dashboard shows half of that. The first steps then would be a Cloudflare cache rule in front of the Worker, or a bundled feed route. Device copies: the limit goes from 30 to 80 pages (about 10 KB each, under 1 MB of the browser's roughly 5 MB). That way, articles the feed loaded also open offline, and they don't push out pages the reader opened themselves. This replaces the 30 in D14. (D14's 15 s rule is replaced by D39.) Considered: loading every first paragraph at once (up to 20 requests on every open, mostly for items never seen). Also considered: a proxy route that returns a whole feed in one response. That means fewer requests, but the Worker would have to read the pages (against D10), and the app and the Worker would have to change in step. Leaving the first paragraph out would be cheapest, but the owner asked for it.

### D27 · 2026-10-23 · A feed stays as it is until the reader refreshes it
A feed is a snapshot kept in memory (`src/feed/`), not a live view of the pages. When it's first built, it waits for the network (showing a skeleton) and uses the device copies only if there's no connection. After that, new data never changes or reorders the list. Only the refresh button or pulling the list down does. The snapshot also remembers each feed's scroll position and which items are on screen. So coming back from an article, switching tabs or switching chips shows the same content in the same place, even if the list screen was taken down in the meantime (which happens on the web and on Android when memory is short). Restarting the app or reloading the web page builds a fresh feed. (Amended by D39: when the reader returns, the app re-fetches, and a changed list is offered with "Päivitä lista".) Considered: relying only on the navigator keeping the list screen alive. That's simplest, but the position is lost when the screen is taken down, and it doesn't stop background refreshes from reshuffling the list. Also considered: saving the snapshot to the device. It would survive restarts, but it would also greet the reader with yesterday's list the next morning.

### D28 · 2026-10-23 · "Next" in an article follows the list it was opened from
The address tells an article which list it came from: `/105?feed=uutiset`. The footer's next card shows the following item in that feed's snapshot (section, page number and headline, all already known, so no extra request), and ‹ goes to the previous one. Tapping next replaces the article instead of adding a history step, so one Takaisin always returns to the list. Etusivu's lists work the same way (`?feed=etusivu`, lead first, then the groups). With no list behind it (a link, a favourite, the jump sheet, a shared link, or a reloaded page whose snapshot is gone), the footer stays as it is today, built from Yle's previous and next page numbers. Why not Yle's next page: it's just the next number. At a section's end it's the next section's index page (130 gives 113 as its previous page), and it can be a page that's missing right now (104 answered 404 while 102 listed it). Headlines in the card are clamped on screen to 2 lines, never cut in the text. Considered: adding a history step for each next (ten stories would need ten Takaisin presses), and keeping the list context only in memory with nothing in the address (a shared or reloaded link would then show the wrong neighbours).

### D32 · 2026-10-24 · Anonymous page counts in the proxy, with no cookies and no accounts
The owner wants to know which pages are read most and how many readers there are a day. This replaces the earlier "no analytics" line in `AGENTS.md`. The word "anonymous" is replaced in part by D45 (the daily visitor code is pseudonymous). **Rules that don't bend:** no cookies and so no consent banner, nothing stored on the reader's device for counting, no account ever, no IP address or other personal data kept. **How:** the proxy already sees every request, so it counts there (Cloudflare Workers Analytics Engine, queried with SQL). Each counted request writes one small record: page number, cache state, country, platform (web or app) and a daily visitor hash. The hash is made from the IP address and browser type plus a secret salt that changes every day, so the same reader looks like a new one each day. The IP address itself is never written down. **What it can and can't tell us:** readers per day, yes, roughly (phones on the same mobile network can share an IP and count as one, and one person switching between wifi and mobile counts twice). Returning readers over several days, no. That is the price of keeping nothing on the device. **Only real reads are counted:** one proxy request is not one read. A feed fetches about 20 pages for its first paragraphs (D26), and screens retry. So the app labels the pages the reader deliberately opens, and the proxy counts only those. The label carries no user information. **Reading the numbers:** the owner doesn't write SQL, so a `stats` script prints top pages, readers per day, countries, platforms and Yle requests per hour in plain text (AN.4). It needs a Cloudflare API token that can only read analytics. **Honest limits:** this is not legal advice. Counting without cookies or stored IPs is generally the low-friction route in the EU, but Cloudflare itself still sees IP addresses as our host, and the privacy text (AN.3) says so; someone qualified should check the wording before store submission, and the Google Play Data safety form must match. Analytics Engine keeps data for a limited time (about three months; to be confirmed when building), which fits, since only totals matter. The free-tier limits are checked when AN.1 is built. Analytics must never slow down or break a response. Work: AN.1–AN.4 in the backlog. **Considered:** Cloudflare Web Analytics (cookieless, but it adds a script to the web page and doesn't cover the Android app, and the owner wants counting to be purely server-side); a random install ID saved in the app (it would count returning readers, but it's data stored on the device, which falls under the same consent rules as cookies and breaks the owner's promise); relying only on Cloudflare's built-in traffic graphs (free, but shallow on the free plan and no split by app or by real reads); not counting at all (simplest, but the owner can't see what readers want).

**Update (AN.1, 2026-10-24):** built differently from the first sketch, for three reasons. (1) **A separate "opened" call, not a label on page fetches.** The app tells the proxy with `POST /v1/opened/{page}` (no body, no custom headers, so the browser sends no preflight) when a reader opens a page. A label on the fetch would be missed whenever the page came from the app's 15 s copy or the browser's 15 s cache, and it would count feed prefetches and retries. The answer is always `204`. The platform is `web` when the request has an Origin header and `app` when it doesn't; opens from an Origin outside `ALLOWED_ORIGINS` are not counted. (2) **Yle requests are counted too**, every one the Worker sends with its outcome (`ok`, `not-found`, `timeout`, `failed`, `status-401`…), so we can see the 300-an-hour limit coming. (3) **No cache hit rate.** Counting every served request would double the writes. **Limits (read from Cloudflare's docs on 24.10.2026):** Analytics Engine free plan: 100,000 data points written a day and 10,000 read queries a day; data kept three months; Cloudflare says billing may start "in the coming months", so check before relying on it. The Worker free plan's 100,000 requests a day (D26) now also counts the extra call per opened page. When a limit is hit, counting just stops or gets sampled; readers are not affected. **The hash** is an HMAC-SHA-256 of the day, IP address and browser string, keyed with a Worker secret (`ANALYTICS_SALT`), cut to 32 characters. That is at least as strong as the sketched "hash with a daily salt", and needs no stored salt. **Known weakness:** anyone with a script can post opens without an Origin header and inflate the numbers or use up the day's writes. It can't break readers' answers. If it happens, a free Cloudflare rate-limiting rule in front of `/v1/opened/` fixes it without code.

### D44 · 2026-10-25 · Content-Security-Policy for the web app: strict for scripts, loose for styles
**Why:** before the repo goes public (D41), satanen.io needs a CSP and HSTS, and the proxy needs `nosniff` on every reply. A CSP limits what an injected piece of HTML could do.
**Decision:** `public/_headers` sends `default-src 'none'`, with scripts, fonts, manifest and the service worker from our own origin only (`'self'`); connections and images also to `https://api.satanen.io`; images also `data:`; `object-src 'none'`, `base-uri 'self'`, `form-action 'none'`, `frame-ancestors 'none'`. No `unsafe-inline` or `unsafe-eval` for scripts: the Expo export has no inline script (checked in `scripts/smoke-web.mjs`, which fails if one appears). Localhost is not in the policy, since a production build must not call it (see `scripts/check-dist.mjs`). HSTS is one year, without `includeSubDomains` or preload, so it cannot lock out another subdomain. The proxy adds `X-Content-Type-Options: nosniff` to every response in one place (`handle` in `proxy/src/index.ts`), with a test.
**Styles use `'unsafe-inline'`:** React Native Web and expo-font add `<style>` elements while the app runs (one per group of rules and per font), with text that is only known at runtime. I tried a hash for the one inline `<style>` in `index.html`: Chrome then blocked about ten runtime style elements, each with its own hash. Nonces need a server-rendered page, which a static site does not have. Inline styles cannot run code, so the risk is small next to scripts, which stay strict.
**Considered:** hashing every style (not possible at build time); dropping the style CSP (the `unsafe-inline` for styles costs less than losing the rest of the policy); a build-time rewrite of the Expo output (fragile).
**Tested:** production build served with `wrangler dev`, loaded in Chrome: `/`, `/105`, the jump sheet and the drawer, with zero CSP violations, the service worker active and the six fonts loaded.

### D45 · 2026-10-25 · Privacy texts call the daily visitor code pseudonymous; shorter code; request logs off
The proxy's daily visitor code is a keyed hash of the UTC date, IP address and browser type. Within one day the same reader gets the same code, so it is a pseudonymous identifier, not "nothing identifying". D32 and the texts called the counts "anonymous"; that was too strong. **Decision (wording route):** the in-app Tietoja text, both privacy policies, the Play listing draft and the owner checklist now say plainly what it is: a daily code made from connection and device details, changing every day, not linkable across days, raw IP and device details never stored, no cookies, nothing saved on the phone, used only to count readers per day. The word "nimettömästi" is gone. **Why not a salt kept in storage (KV) that is rotated daily:** the secret key plus the date in the hash already makes days unlinkable, and nobody can reverse the code without the key; a stored daily salt would add a failure point and KV write limits (D11) for no change in what is true. The wording was the dishonest part, not the method. **Also:** the code is cut from 32 to 12 hex characters (48 bits), enough to tell a day's readers apart and too short to work as a fingerprint of an IP address. `[observability]` is set explicitly to `enabled = false` in `proxy/wrangler.toml`, so no Workers Logs hold request details; turn it on only while hunting a fault. The cache statement in the policies now matches D39 (per kind of page: 1 min, 2 min, 5 min, 30 min; 404 30 s; errors never cached). **Not legal advice (D32):** the owner should have the final wording checked by someone qualified before the policy is published.
